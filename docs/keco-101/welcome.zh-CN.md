## Keco 是什么

Keco 是**为做游戏服务的工作台**。

它要解决的不是"文档存哪儿"，而是一个更具体的问题：**你脑子里的那个游戏，怎么一步步变成能跑起来、能被人玩、能被打分的东西。**

一句话说清它的位置：

> 你写下设计，Keco 把设计变成数据和素材，交给 Godot 做成可玩切片，再用一套固定标准打分，告诉你下一步该修什么。

## 一条主线：从设计到可玩

Keco 把游戏制作拆成六个阶段，每个阶段的产出都是下一个阶段的输入：

```
① 写设计        GDD、玩法说明、Roadmap
      ↓
② 变数据        角色表、敌人表、物品表、关卡表、掉落规则
      ↓
③ 备素材        本地图片导入、PixelLab 像素生成
      ↓
④ 做切片        在 Godot 里实现一个能玩的最小玩法
      ↓
⑤ 做测评        按固定标准打分，列出问题清单
      ↓
⑥ 整改复评      修完只复测受影响的部分
      ↓
   回到 ①，进入下一个切片
```

关键在于**这六步共用同一份项目数据**。设计文档改了，从它生成的表能跟着演进；表里的数值变了，Godot 里读到的就是新值；测评发现的问题会写回项目，成为下一轮的开发来源。不再是"文档一份、Excel 一份、素材文件夹一份、代码里又抄一份"。

## 你的项目里装着什么

```
Keco 项目
├── 文件夹、文档、故事图、搜索       ← 设计与规划
├── 表格、字段、行、关联、图片       ← 游戏数据
├── 本地图片资产                     ← 已有素材
├── Godot Slice 规划与开发           ← 实现
├── PixelLab 像素素材                ← 生成素材
└── EDD 游戏测评                     ← 质量把关
```

这就是 Keco 的全部能力范围。所有内容都挂在**同一个项目**下，所有改动都基于稳定 ID，而不是靠名字猜。

## 两种用法，同一份数据

Keco 有两个操作入口，用哪个取决于你在做什么：

| | **网页端** | **AI 客户端**（Claude Code / Codex + Keco 插件） |
| --- | --- | --- |
| 适合 | 手写文档、手填表格、看剧本分支、跑数值模拟 | 批量生成表、导素材、写 Godot 代码、跑测评 |
| 谁常用 | 策划、编剧、数值 | 程序、技术策划 |
| 特点 | 所见即所得，改完即时同步 | 说一句话完成一整套流程，每步有确认和验证 |

同一个项目，两边看到的是同一份数据。策划在网页上改了角色数值，程序在 AI 客户端里读到的就是改完的值。

## 三个核心概念

1. **项目（Project）** —— 一款游戏的工作空间。你的所有文档、表、素材、切片计划、测评报告都在里面。工具始终在"当前选中的项目"里工作。
2. **文档（Document）** —— 协作式 Markdown。GDD、Roadmap、切片规格、开发状态、测评报告都是文档。
3. **表（Table）** —— 结构化的游戏数据。一行一条数据，列有明确类型，表之间可以互相引用（角色引用技能、关卡引用敌人、敌人引用掉落）。

---

## 它不做什么

说清边界，比夸大能力有用：

- **不会一键生成一款完整的商业游戏。** 它覆盖"设计 → 数据 → 素材 → 切片 → 测评 → 整改"这条链路，但完整地图设计、玩法取舍、好不好玩的判断、发布工程，仍然要人来定。
- **不会替你判断"好玩"。** 测评环节要求真实的运行记录和玩家反馈；拿不到证据时，它会标记"需要人工确认"，而不是默认通过。
- **不会悄悄改东西。** 高成本或不可逆的操作一律先预览、先确认；写完之后会重新读一遍来验证，而不是看到接口返回成功就宣布完成。
