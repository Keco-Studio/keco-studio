# Document Import And Asset Writeback Repair Design

**Date:** 2026-08-24

## Goal

Repair the current Keco document resource-import and local-image writeback
flows on the `8-23debug` branch without changing the existing visual direction
decision: a new Game Design System starts with the Pixel Art preset as its
initial value. Custom art direction, reference games, and avoid guidance remain
optional; no custom art is generated by this change.

The release must be verified through the same path a user uses:

1. Open a prepared document in a project that also contains another non-empty
   document and a populated table.
2. Open the document editor's top-toolbar **Insert reference** action.
3. For a table, show the actual rows and preserve every selected row's values.
4. For a document, show selectable text and preserve the exact selected range.
5. Through the Keco MCP connection, import a local image file into an existing
   compatible project table and read the written object back.

## Current Failures

- `listTableReferenceSources` filters only `document_export_type = script`.
  Historical conversation libraries can have a missing export type while still
  carrying `source_document_id`, so they appear as tables and their rows look
  like a nonexistent table.
- Document reference blocks depend on normalized collaborative Yjs state.
  Older or freshly created documents can still have useful content in the
  legacy `documents.content` column while the transport state is empty or
  yields no blocks, leaving the picker with “No matching content”.
- The local-image workflow is documented, but the release acceptance must prove
  the complete writeback contract rather than treating successful upload PUTs
  as completion. The verified image object, row values, and paginated read-back
  are the success criteria.

## Design

### Art Style default

`DEFAULT_GAME_ART_STYLE_KEY` remains the initial selection in the creation form.
The review summary displays Pixel Art and its current preset revision when the
user leaves the optional customization fields empty. Existing validation still
rejects a partially filled visual-reference row, but an empty reference list is
valid. No new default or custom visual asset is introduced.

### Reference source filtering

Extend the library source projection to read `source_document_id` together with
`document_export_type`. A source is referenceable as a table only when:

- it belongs to the current project;
- it is not a conversation (`document_export_type === 'script'`); and
- it is not a malformed derived conversation row where
  `source_document_id` is present but `document_export_type` is null.

The same predicate is applied when loading a selected library's rows, so a
stale client cannot bypass the picker filter by retaining an old library ID.
The picker shows the source table's real ordered fields and rows, preserves
row order, and inserts the stable row IDs plus all cell values. A source-query
failure is visible and does not silently render an empty table.

### Document text fallback

`listDocumentReferenceBlocks` continues to prefer normalized Yjs blocks and
project-scoped access checks. If the normalized state has no selectable blocks,
it reads the authoritative document Markdown/content and creates deterministic
paragraph/heading preview blocks with stable UUIDs derived from the document ID
and block index. The fallback is preview-only until the existing normalization
path can persist block IDs; selection still serializes the exact text before and
after the range. Empty documents continue to show “No matching content”.

The fallback must never expose the open document, cross-project documents, raw
Yjs payloads, or a synthetic block for whitespace-only content. Existing range
resolution and reference revalidation remain authoritative before insertion.

### Local-image MCP writeback

The existing MCP schemas remain the source of truth. The acceptance workflow
uses an isolated temporary user and an existing project/table fixture so no
existing user content is deleted or overwritten.

For each supported image:

1. Inventory local file name, media type, and byte size; reject unsupported or
   duplicate names before mutation.
2. Read the exact project, table schema, and target row match key.
3. Ask for/record the write preview and confirmation.
4. Call `prepare_image_uploads` with metadata only.
5. PUT exact bytes to each returned signed target outside MCP, using every
   returned method/header.
6. Call `complete_image_uploads` with only the returned `image.path` values.
7. Write each complete verified image object into the image field using the
   stable row key.
8. Paginate-read the table and assert every input file has exactly one matching
   row, the image object is complete, and no unrelated row changed.

Signed URLs, headers, bearer tokens, local paths, and raw bytes never enter MCP
arguments, checkpoints, logs, or final reports. A failed item is reported as
failed and does not make the batch look successful; completed items are reused
on retry instead of being uploaded again.

## Error handling

- A filtered conversation library is absent from the picker and a stale direct
  selection returns a clear unavailable-source error.
- A document with no content shows an empty-state explanation; a document with
  legacy content shows selectable blocks rather than a false empty state.
- Upload preparation, PUT, completion, row write, and read-back failures remain
  item-scoped and include the stable error code and next recovery action.
- Temporary acceptance fixtures are cleaned up in `finally`; cleanup failures
  are reported separately and never hidden behind a success message.

## Verification

- Unit tests cover the table-source predicate, stale source rejection, legacy
  document-content fallback, exact range labels, and default Pixel Art review.
- Existing document-reference and MCP image tests remain green.
- A focused browser acceptance covers table row selection, document text-range
  selection, persisted reference text, and no console/page/5xx errors.
- A remote production MCP acceptance performs the isolated image writeback and
  authoritative read-back, reporting all created stable IDs and errors without
  deleting pre-existing content.

## Non-goals

- No new art-style presets, custom art generation, or visual asset authoring.
- No broad document editor rewrite or new persistence format.
- No automatic deletion, overwrite, or renaming of existing Keco content.
- No claim of success from discovering a capability or from an upload response
  alone; only authoritative read-back counts.
