# PixelLab Operation Reference

This file is a planning reference, not a substitute for live MCP schema discovery. The live tool list and input schema always win.

## Capability Map

Capability keys, official endpoints, live adapters, and the canonical `assetKind`
vocabulary all live in the shared [PixelLab capability registry](../../../references/pixellab-capability-registry.md). Read it
first; this table only records what each map need requires in the manifest.

| Map need | `assetKind` | Capability key | Required planning fields |
|---|---|---|---|
| reusable grass, dirt, water, sand, and transition terrain | `tileset` | `top-down-tileset` | prompt, tile size, style/reference, terrain/edge rules, output format |
| roads, rivers, bridges, paths, and junctions | `tile` | `tiles-pro` | prompt, tile size, four-direction edge semantics, caps/corners, output format |
| floors, walls, doors, columns, roofs, and interior parts | `tile` | `tiles-pro` | prompt, tile size, module dimensions, style/reference, output format |
| a single tree, house, rock, chest, sign, or prop | `image` | `pixflux` or `bitforge` | prompt, object bounds, transparent background, style/reference, output format |

Names such as `create_topdown_tileset`, `create_path_tiles`, `create_building_kit`,
and `create_map_object` are **not** live MCP tool names. They were planning labels
only. Resolve the live adapter and its arguments at runtime, record the observed
tool name and `compatibility` in the manifest, and never invent parameter names.
Several of these capabilities currently have no adapter; the registry records
which, and an `unavailable` capability blocks the asset before any write.

## Manifest Template

```yaml
runId: local-YYYYMMDD-HHMMSS
sliceId: map-assets
assetKey: unique-key
kind: tileset|path|building-kit|map-object
purpose: exact gameplay or art purpose
providerCapability: capability key from the shared registry
operation: live MCP tool name
compatibility: exact|fallback|unavailable
prompt: exact prompt without secrets
references:
  - path: project-relative path
    sha256: hash captured before generation
dimensions:
  tileWidth: 16
  tileHeight: 16
  atlasWidth: null
  atlasHeight: null
transparency: true|false
expectedFiles: []
targetPaths: []
collisionOwner: godot
status: planned|ready|failed|blocked
```

For development intent, write and read back the planned registry row before generation. The row must resolve the project's actual semantic field labels and IDs for the stable key, kind, purpose, target path, width, height, transparency, operation, prompt, references, `runId`, `sliceId`, and status. After validation, persist the complete verified Keco image object and read back the ready row before downloading authoritative bytes for Godot.

## Validation Notes

For tilesets, verify tile dimensions, atlas alignment, seam continuity, and Wang/corner metadata. For paths, verify all required edge combinations and junctions. For building kits, verify module alignment and that doors/windows do not introduce hidden collision assumptions. For objects, verify alpha, anchor/origin intent, and the visible footprint used for manual collision.

Keep generated bytes temporary until validation passes. Do not commit API keys, signed URLs, or opaque provider job credentials.
